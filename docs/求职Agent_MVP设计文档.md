# ProgressAgent（求职成长 Agent）—— MVP 产品设计文档 v0.7

> 一句话定位：**一个由目标岗位 JD 驱动、以真实检测为依据、能够自我演进的个人求职能力成长系统。平时系统自行研究市场带你巡航训练；当你某天看到意向岗位并甩来 JD，它切换攻坚模式做针对性训练，划定面试准入分——达标才建议你去面试。**
>
> 它持续回答你三个问题：我该学什么？我还差什么？我下一步做什么？并用自己的使用数据驱动自己变得越来越好用——直到比你的原始想法更优。

---

## 1. 目标用户与要解决的问题

### 用户画像

- 传统 Go 后端工程师，正在补齐 Python 工程能力，目标岗位聚焦：**Agent 应用开发**（市场上该类岗位普遍要求 Python，主流 Agent 框架也以 Python 为主）。
- 当前状态：**已离职全职求职**，时间窗口 2–3 个月，每日可用约 4 小时。
- 困境 1：网上学习材料过载，不知道哪些是岗位“高度共用”的知识，无从下手。
- 困境 2：没有清晰路径导致自控力差，最终干脆不学。
- 诉求：一个能检测真实水平、指导学习、模拟面试、全程陪跑的“求职保姆”。

### 核心洞察

1. **“学什么”的答案不在网上，在你的目标岗位 JD 里。** 从 JD 反向拆解能力要求，资料过载问题自然消失——系统就是过滤器。
2. **自控力不靠意志力解决，靠结构。** 小步任务 + 定期检测 + 外部锚点，比“自律”可靠。
3. **“检测真实水平”必须基于可验证的工程任务，并控制 AI 辅助程度**——不能只是知识问答，也不能让 AI 生成的代码污染检测结果；否则水平报告就是自欺欺人。
4. **这个系统本身就是一个真实的 Agent 实战项目。** 用市场上 Agent 工程师的通用语言 Python，亲手造一个会自我演进的 Agent 系统，学到的每个概念都会立刻在自己的产品里被使用，远比刷教程高效；它也具备成为求职作品集的潜力（v0.6：先作为私有工具运行，公开与否日后单独决策）。
5. **系统要自我演进。** 它收集使用信号，沉淀反思，自己提出改进提案，经人审阅后合入，功能越来越接近你的想法，并能提出你没想到的、被数据支持的改进。
6. **用户一开始不会提供 JD。** 因此“JD 采集”不是附加功能，而是系统的第一个自动化能力：自己联网寻找真实 Agent 开发岗位 JD，聚合成岗位画像，据此做基础检测与训练；当用户给出具体 JD 时，再切换到个性化模式。
7. **用户不会定期喂 JD，只有“突然看到意向岗位”时才发来。** 所以 JD 的出现是事件，不是日常输入；系统收到 JD 后必须从“巡航训练”切换为“对岗攻坚”，并设一道硬性准入闸门：系统测验达标才允许投递与面试。

### 起点基线（v0.7，等待独立检测校准）

用户自评：Python 只会常见语法；[rag-demo](https://github.com/hju-wang/rag-demo) 中有较多 AI 生成内容，因此**不能作为独立能力的强证据**，只能当作“接触过的技术栈清单”：

- **接触过（不代表掌握）**：Python 3.12 + uv、文档加载/分块、FAISS + BM25 混合检索、rerank、FastAPI（REST + SSE）、Streamlit/Vue、pytest/ruff、基本 Agent 上下文与 RAG 概念。
- **真实掌握程度未证实**：由于 AI 参与度高，独立编码、调试、解释设计决策、排查问题的能力都还未知，需要受控检测来校准。
- **学习主线不从语法出发**：不从头教 Python，直接围绕 Agent 开发工程师所需技术展开——function calling / tool use、Agent 编排（单/多 Agent）、MCP、RAG 实战、评测与可观测等；只有检测暴露 Python 基础缺口时才按需补漏，不作为主线。
- **Go 后端工程素养**：并发、可靠性、可观测性心智仍是差异化资产，但同样需要能独立用 Python 表达才算数。
- 结论：**第一次检测必须包含“受控条件下的独立任务”**（限时、明确 AI 辅助边界），先把基线校准到真实水平；基线未校准前，出卷难度默认保守，宁可低估不可高估。

## 2. 产品内核：一条成长闭环

整个产品只有一件事：**跑通一条可循环、可量化的成长闭环**。

```
目标岗位 JD（系统自动采集 / 用户可补充）
    │  ① 拆解
    ▼
能力模型（岗位需要什么）
    │  ② 检测
    ▼
当前水平（我现在在哪）
    │  ③ 差距分析
    ▼
差距报告（差什么）
    │  ④ 规划
    ▼
个性化学习路径（下一步做什么）
    │  ⑤ 执行 + 督促
    ▼
实操 / 学习 / 复测 / 面试模拟
    │  ⑥ 沉淀
    ▼
使用数据与反馈
    │  ⑦ 反思
    ▼
自我演进提案 → 审阅合入 → 系统升级 → 回到 ①（更准、更高效）
```

### 闭环中的关键动作

1. **采集目标**：系统自动联网采集真实 JD，去重清洗后聚合为岗位画像（哪些能力被高频、高等级要求）；用户可补充或指定具体 JD，优先于基准画像。
2. **拆解**：岗位画像 / JD → 能力权重清单（哪些必须会、哪些加分）。
3. **检测**：知识、实操、表达三层检测当前水平。
4. **差距分析**：输出“差距报告”，每项给出差距证据与优先级。
5. **规划**：生成按周拆解的学习路径，任务具体、可验证。
6. **执行**：保姆式督促：今日任务、完成打卡、连续进度。
7. **复测**：周期性复测 + JD 驱动 mock 面试，验证提升。
8. **演进**：每次使用沉淀数据 → 反思 → 改进提案 → 系统自己变强。

### 两种使用模式：巡航与攻坚

| | 巡航模式（默认，长期运行） | 攻坚模式（事件触发） |
| --- | --- | --- |
| 触发方式 | 无 JD，系统自动联网研究市场 | 用户某天看到意向岗位，发来 JD 链接或文本 |
| 目标 | 打牢 Agent 开发通用能力，维持基线水平 | 针对该 JD 精确补齐差距，达到面试准入线 |
| 检测 | 定期基准自测（能力模型驱动） | 基准检测 + 按该 JD 权重加权的 mock / 实操 |
| 学习计划 | 通用学习路径 | 倒排冲刺计划，围绕该 JD 的能力权重展开 |
| 放行条件 | 无 | 面试准入闸门：达到系统设定分数并保持，才建议投递/面试 |

### 攻坚模式与面试准入闸门

用户发来意向 JD 后，系统执行一次完整的“对岗攻坚”流程：

1. **立即解析**：拆解该 JD 的能力要求与权重，与现有岗位画像比对，识别“这个岗位特有的加分点”。
2. **立即检测**：跑一次准入基线测试，输出 0–100 的“当前距该 JD 的准备度”及各维度分数。
3. **出卷并设定准入线**：系统按该 JD 自动出一张 100 分制准入试卷（题目构成与权重由 JD 的能力要求决定，例如 JD 强调 Python 实操则实操占分更高），并给出“面试准入线”（总分线 + 每个硬性维度下限）与所需冲刺时长。
4. **生成冲刺计划**：按可投递时间倒排训练；安排多次 gate 测试（如隔天 mini mock + 每周一次全真测评）。
5. **闸门判定**：连续两次准入测试达标 → 亮“可投递”绿灯（有效期 2 周，附临场弱点清单供复盘）；未达到 → 亮红灯，明确说明还差什么、预计还要多久。绿灯过期后需重新检测达线方可恢复。

两条纪律必须写进产品：

- **总分不兜底**：即使总分达标，若某个 JD 硬性要求维度低于下限（例如 Python 实操被硬性要求），依然不放行——否则会拿着真实缺陷去送面试。
- **准入线必须被校准，不能拍脑袋**：初始阈值由 JD 标注的难度/经验要求 + 校准性全真 mock 确定；之后用你真实面试的结果回流修正。若系统打分与真实面试反馈长期不一致，演进引擎必须优先修订评分与准入逻辑。

## 3. 关键设计原则

| 原则 | 含义 |
| --- | --- |
| 以终为始 | 一切从目标 JD 的能力需求出发，不从“网上有什么资料”出发 |
| 检测导向 | 没有检测就不算学会；每个学习项都有对应验证方式；检测需控制 AI 辅助程度，确保反映真实水平 |
| 数据闭环 | 每次交互都沉淀为结构化数据，供分析、督促与演进 |
| 保姆式结构 | 小步、明确、可验证，系统主动推动，而不是等用户问 |
| 自我演进 | “让自己变得更好”是一等功能，不是后续彩蛋 |
| 人工护栏 | AI 负责提案与执行细节，人类负责决策；任何演进都可回滚 |
| 对外克制 | 系统只影响自己的求职训练，不擅自对外投递、发消息、发布 |

## 4. 自我演进机制（重点设计）

### 4.1 演进的四层含义

“自我演进”不是让 AI 随便加功能，而是分四层、由低风险到高风险渐进：

| 层级 | 演进对象 | 示例 | 风险 |
| --- | --- | --- | --- |
| L1 内容资产 | 能力模型、题库、学习资料、知识图谱 | 根据答错数据新增一道高频面试题；修正能力模型里过时的条目 | 低 |
| L2 策略 | Prompt、追问策略、路径生成规则、督促节奏 | 发现用户在某类题上总是卡住，调整追问深度；把每天任务拆得更小 | 中 |
| L3 产品功能 | 新增模块 | 数据表明“简历被拒”是主要瓶颈 → 提案新增简历分析模块 | 较高 |
| L4 元演进 | 演进机制本身 | 改进信号采集方式、提案格式、自测流程 | 需最谨慎 |

MVP 阶段先完整跑通 **L1 + L2**，L3 以提案形式进入路线图，L4 每季度审视一次。

### 4.2 演进闭环（Evolve Loop）

演进循环包含六个环节，每个环节都有明确产出：

1. **采集信号（Signal）**
   自动记录：检测得分与错项、mock 面试中答不好的知识点、学习任务完成率、用户手动纠正、用户补充的想法、关键对话摘要。
   产出：结构化 `signals/` 日志。

2. **沉淀证据（Evidence）**
   定期把信号聚合为可读证据：例如“近两周差距报告中，RAG 相关能力连续 3 次排名第一，但学习任务完成率只有 40%——任务可能太大或太难”。
   产出：证据快照。

3. **生成提案（Proposal）**
   由演进 Agent 基于证据生成改进提案，格式固定：
   - 提案编号、日期
   - 观察到的证据（引用具体数据）
   - 建议改动（改哪个资产/策略/功能）
   - 为什么这会让你离目标岗位更近
   - 如何验证（必须可测）
   - 风险与回滚方式
   产出：`evolution/proposals/` 下的 Markdown 提案。

4. **自测（Self-test）**
   低风险改动自动跑回归（例如题库改动检查格式与难度分布）；高风险改动生成测试清单。
   产出：测试结果。

5. **人工合入（Review gate）**
   你（人类）是最终 Owner：任何合入都必须经过你知情并批准——包括 L1 低风险资产改动，不设自动合入通道。你可以选择采纳、拒绝或修改。代码与资产改动一律走 git，可 diff、可回滚。
   产出：合并记录 + CHANGELOG。

6. **版本化（Versioned）**
   能力模型、题库、Prompt 全部版本化；每次演进记录在 CHANGELOG，形成“这个系统如何一步步长成今天这样”的完整档案。
   产出：版本历史（这本身就是面试素材）。

### 4.3 如何保证演进方向“比想法更优”而不是跑偏

系统需要三个约束器，防止“自嗨式演进”：

1. **北极星锚点**：任何提案必须回答——它是否让你离目标更近、如何测量。近期目标：拿下 **Agent 应用开发** offer；远期目标：把训练方法沉淀为可帮助更多人的产品。MVP 阶段的提案以近期目标为准绳，答不上来的一律降权。
2. **证据门槛**：功能级提案（L3）必须有数据或明确场景支撑，而不是模型觉得“酷”。
3. **预算约束**：演进也要尊重你的时间与算力成本；系统同时维护一个“当前阶段不做清单”，避免范围失控。

此外，让系统有机会超过你的原始想法，需要两条规则：

- **想法是活的**：`想法.md` 和本文档都纳入版本管理；当使用数据与你的原始假设冲突时，系统可以提案修订需求本身（例如：数据表明实操能力比知识广度更影响面试结果，建议把重心调整）。
- **惊喜提案通道**：允许系统提出你从未想过、但有证据支持的方向（如“后端可靠性与可观测性的工程素养，是你区别于纯 Python 选手的差异点，建议在作品集里显性化”）。它的价值在于发现你自己没意识到的模式。

## 5. 功能模块与 MVP 范围

### P0 —— MVP v0.1（先跑通最小闭环）

| 模块 | 功能 | 验收标准 |
| --- | --- | --- |
| F0 JD 采集与岗位画像库 | 自动联网搜索真实 Agent 开发 JD + 人工种子库 → 去重清洗 → 岗位画像 | 无需用户输入即可提供“目标岗位到底要求什么”的量化画像 |
| F1 能力模型库 v1 | Agent 开发工程师能力地图（JSON + 文档，版本化），由岗位画像持续校准 | 能覆盖至少 6 大维度；每个能力项有检测方式 |
| F2 水平检测 v1 | 三层检测：知识自测、实操小任务骨架、基础面试问答 | 输出结构化水平报告，能看到薄弱项 |
| F3 差距分析 | 基准画像（无用户 JD）/ 用户 JD（个性化）→ 与检测结果比对 → 差距报告 | 不给 JD 也能输出差距报告；给 JD 后自动个性化 |
| F4 学习任务与督促 | 按周任务列表、打卡、连续进度、提醒 | 用户能说出“我这周做了什么、下一步做什么” |
| F5 演进管道 v1 | 信号采集 + 每周反思 + 提案生成 + 人工审阅 | 每周至少产出若干条有证据的改进提案并记录采纳情况 |
| F6 攻坚模式与准入闸门 | 用户发来意向 JD → 专属差距报告 + 按 JD 出 100 分制试卷 + 冲刺计划 + 多次 gate 测试 → 准入判定 | 未达准入线时明确输出“不建议投递/面试”及差距；连续两次达标输出有效期 2 周的绿灯与临场弱点清单 |

### P1 —— v0.2（增强检测与求职支持）

- 实操任务自动评测（给任务 → 跑结果 → 自动/半自动打分）。
- JD 驱动模型面试官增强：按岗位画像 / JD 权重出题、多轮追问、按弱项动态深挖。
- JD 库自动刷新：定期搜索增量 JD，新需求自动纳入画像，过期 JD 自动降权。
- 真实面试结果回流：用实际面试表现校准准入线与评分标准（反哺演进引擎）。
- 简历与项目叙事打磨：基于目标 JD 优化简历要点与 STAR 案例。
- 求职漏斗跟踪：投递 → 笔试 → 面试 → 结果，沉淀每轮真实反馈。

### P2 —— 远期（自适应与自治）

- 基于知识图谱的自适应学习路径（动态跳过已掌握内容）。
- 提案与自测更自治，但合入仍须人工批准——演进增强发生在提案质量与测试覆盖上，不发生在合入权限上。
- 求职决策助手：offer 对比、薪资谈判、岗位选择。

## 6. Agent 开发工程师能力模型 v0.1（草案）

这是整个系统的地基，也是“学什么”的唯一答案来源。先按六维建模，后续由演进引擎持续修订。

| 维度 | 核心内容 | 主要检测方式 |
| --- | --- | --- |
| A. 大模型基础与应用 | 模型能力边界、上下文管理、结构化输出、提示工程、Function Calling、RAG 概念 | 知识题 + 面试问答 |
| B. Agent 框架与编排 | Agent 循环（ReAct/Plan-and-Execute）、工具调用循环、多 Agent 通信与编排、状态管理、长任务容错 | 实操小任务 + 系统设计题 |
| C. 工具与生态 | MCP、工具 Schema 设计、RAG/Embedding/向量库、记忆、权限与沙箱 | 实操任务 + 面试问答 |
| D. 评测与质量 | Eval 数据集、LLM-as-Judge、Trace/可观测、Guardrail、安全、成本与延迟 | 实操评测任务 + 案例答辩 |
| E. Python 工程能力（硬门槛） | Python 语言惯用法与类型标注、async 并发、FastAPI、pytest、依赖与打包管理；将 Go 阶段积累的可靠性/可观测性心智迁移到 Python 工程 | 代码小任务 + 代码审查 + 系统设计题 |
| F. 求职交付 | 项目叙事（STAR）、架构表达、JD 对齐、面试沟通 | Mock 面试打分 |

> 语言决策（v0.2）：调研真实 JD 后确认，市场上 Agent 开发岗位普遍要求 Python，主流 Agent 框架也以 Python 为主，因此 **Python 是硬性门槛，不是可选项**。
>
> 差异化定位调整为：你不是从零转行，而是带着后端工程素养（可靠性、并发心智、系统设计）进入 Agent 领域——但这套素养必须能用 Python 生态表达出来。学习的关键不是“会写 Python”，而是掌握 Python 的惯用法（类型标注、async/await、FastAPI、pytest、依赖与打包），避免写出“翻译成 Python 的 Go 代码”。

## 7. 技术架构（草案）

```
┌─────────────────────────────────────────────┐
│  交互层：CLI（先） → Chat / Web（后，作品集展示）│
└──────────────────┬──────────────────────────┘
                   ▼
┌─────────────────────────────────────────────┐
│  Agent 核心（Python）：调度、会话、工具调用      │
│  ├─ JD 采集/解析/岗位画像（自动联网搜索）       │
│  ├─ 检测引擎（知识题 / 实操任务 / 评测脚本）    │
│  ├─ 面试引擎（JD 驱动、动态追问）              │
│  ├─ 路径规划与督促                           │
│  ├─ 进度追踪                                 │
│  └─ 演进引擎（信号 → 反思 → 提案 → 自测）      │
└──────────────────┬──────────────────────────┘
                   ▼
┌─────────────────────────────────────────────┐
│  数据与资产层                                 │
│  ├─ Git 版本化资产：能力模型 / 题库 / 评测任务 / │
│  │   Prompt / 提案（可 diff、可回滚）           │
│  └─ SQLite：用户进度、检测记录、面试记录、信号    │
└──────────────────┬──────────────────────────┘
                   ▼
┌─────────────────────────────────────────────┐
│  外部依赖：DeepSeek API + 网络搜索（JD 采集）    │
└─────────────────────────────────────────────┘
```

### 技术选型理由

- **Python 为核心语言**：市场 JD 与主流 Agent 框架（如 LangChain、LlamaIndex、OpenAI Agents SDK）都以 Python 为主，做这个项目本身就是在实战中补齐 Python 能力。
- **Go 是资产不是负担**：不需要丢掉已有的后端工程素养，但要有意识地把并发、可靠性、可观测性的心智用 Python 生态重新表达（async/await、类型系统、FastAPI、pytest），而不是机械翻译 Go 的写法。
- **知识资产进 Git**：能力模型、题库、Prompt 都是“代码”，可评审、可测试、可回滚，这是自我演进机制的地基。
- **SQLite 起步**：单人使用足够，避免早期被基础设施拖累。
- **LLM：默认 DeepSeek（OpenAI 兼容）**：为找工作服务，算力成本不作为约束；通过统一抽象层接入，后续可对比 / 切换 GPT、Claude 等模型。

## 9. 成功指标

- **能力可测性**：自测报告与 mock 面试表现一致（不自欺）。
- **学习有效性**：每周任务完成率 ≥ 70%；复测得分呈上升趋势。
- **检测有效性**：mock 面试分数与实际面试反馈相关。
- **自我演进有效性**：提案采纳率、每轮使用后的系统改进数、能力模型修订频次。
- **终极目标**：从“能力报告”到“目标岗位 offer”的时间可测量、可缩短。

## 10. 关键决策记录（v0.6 确认）

1. **目标岗位聚焦：Agent 应用开发。** 岗位画像、能力模型与 mock 题库默认以此方向为主；JD 库仍持续覆盖相邻岗位，用于校准通用能力。
2. **产品形态：CLI 先行**，跑通闭环后再做 Web 端作为作品集展示。
3. **LLM：默认 DeepSeek（OpenAI 兼容）。** 为找工作服务，算力成本不作为约束；保留抽象层方便日后对比与切换。
4. **合入权限：所有合入都必须经过用户知情并批准**，不设自动合入通道。
5. **JD 采集默认方案（可调整）**：不直接“爬”招聘网站——很多站点有反爬与条款限制，容易违规或被封。MVP 采用“搜索引擎 / 公开网页检索 + 真实 JD 种子”的半自动采集：新 JD 入库前先经你确认，之后定期增量刷新。等明确了目标渠道再逐步扩展。
6. **准入试卷：100 分制。** 系统根据 JD 自动出卷并定义各题权重，总分与硬性维度下限共同决定是否放行。
7. **绿灯条件：连续两次达标 → 绿灯，2 周内有效**；过期后重新检测达线即可恢复（恢复是否还需连续两次，留待实际使用后微调）。
8. **求职窗口：已离职全职，2–3 个月**，每日可用 4 小时。计划按 8–12 周倒排；单日任务量以 ≤4 小时为上限，任务宁少勿多，防止过载再次触发“干脆不学”。
9. **起点基线：待独立检测校准，不以 rag-demo 为能力证据。** 该项目含较多 AI 生成内容，只作为“技术接触清单”；第一次检测必须包含受控、限时的独立任务来校准真实基线。学习主线直接围绕 Agent 开发所需技术展开，Python 仅按需补漏。
10. **红灯强制执行：阻拦并监督。** 未达准入线时，系统阻止进入“投递辅助 / 面试准备”流程，并监督用户完成必修 gate 测试；未完成则持续提醒并保持红灯，不放行、不代办。
11. **私有工具：默认不公开。** 水平报告、求职数据、JD 库均视为私人数据；将来若转作品集或产品化，另行决策并做脱敏处理。
12. **内容语言：中文为主。** 讲解与推荐材料默认中文；单日主任务控制在 2–3 个，以每日 4 小时为封顶参考。
13. **长期目标：帮助更多人并盈利。** MVP 不做账号与多租户，但模块边界与数据模型保持通用（能力模型、题库、评测记录不绑定个人字段），为将来产品化留后路。

### 长期愿景（简要）

- 第一阶段：2–3 个月内用本系统拿下 Agent 应用开发 offer（北极星不变）。
- 第二阶段（入职后）：把被实战验证的“能力模型 + 自动出卷评测 + 准入闸门 + 自我演进”沉淀为可复制、可服务更多求职者的产品。
- 架构纪律：不为远期过度设计；只做“不绑定个人字段”的低成本预留，避免将来大重构。
