# 检测参考问题 · 面试背诵版 v0.1

- 用法：每个能力项都写成「面试官问 → 你可以直接背的一段」。**加粗的引用块是背诵内容**，其余是追问提示与证据标签。
- 时长：每段背到 30–60 秒；先说结论，再给 2–3 点，最后一句收尾。
- 纪律（重要）：标注【**有证据**】的可以结合自己的项目细节；标注【**无证据**】的只能用
  “我了解 / 我的理解是 / 我计划这么做”，**不要声称做过**——面试官一追问细节就会露。
- 背诵只是起点：背完把里面的例子换成你自己的项目数据。
- 配套：[详细解答版](检测参考问题-详细解答-v0.1.md)（含完整要点与坑）。

## A 大模型基础与应用

### A1 模型能力边界与选型 【无证据 · 用方法论答】

**面试官**：一个场景来了，你怎么决定用哪个模型？

> 我一般按四个维度选型：任务能力、成本、延迟和约束。先判断任务是分类抽取这类确定性工作，还是多步推理和复杂生成——前者小模型就够，后者才上大模型或推理模型。成本和延迟按预算定，约束包括上下文长度、工具调用支持、数据合规和可用性。初选完，我会用自己场景的一小套样本做 A/B，按通过率、单任务成本和 p95 延迟三个指标拍板，同时准备 fallback，防止主模型限流或超时拖垮链路。

**追问“便宜 10 倍但质量降 5% 怎么选？”**
“先按任务分层：低风险、可校验的环节换小模型，关键决策保留大模型；再定质量门槛，只要不低于门槛就用同一套 eval 回归验证。”

### A2 提示工程与结构化输出 【有证据 · Day 1–3】

**面试官**：你怎么保证模型输出是程序能用的结构？

> 我分三层做。第一层是 prompt：角色、目标、约束、输出格式和示例写清楚，并明确边界——信息不足时允许它说不知道。第二层用结构化机制，比如 function calling 或 JSON Schema，把字段、类型、枚举、必填项约束住，而不是口头说“请输出 JSON”。第三层是解析容错：解析失败就带着错误信息重试或降级解析，拿到结果后还要做业务校验，比如范围、枚举和互斥字段。这样模型偶尔跑偏也不会把系统带崩。

**追问“用户输入里带指令怎么办？”**
“把用户输入和检索内容都当数据不当指令，明确声明资料里的指令一律忽略；关键动作再在系统层做权限和校验，不靠模型自觉。”

### A3 上下文管理 【无证据 · 用方法论答】

**面试官**：多轮对话历史无限增长怎么办？

> 我先算 token 预算：system、工具 schema、检索资料、历史和输出各留多少，超了从哪砍要提前定规则。然后分层：system 和最近几轮保留原文，更早的历史滚成摘要，长期事实写到外部存储、用时再检索回来；一次性工具结果用完即弃，检索原文压成要点加引用。任务进度这类关键信息放进结构化 state，而不是聊天历史，断线还能续。顺序上先做结构化状态，再做摘要，最后才考虑扩窗口——窗口大不代表该塞。

**追问“摘要丢信息怎么办？”**
“摘要保留来源引用，关键字段用结构化字段兜底，重要结论不让它依赖摘要复述。”

### A4 Function Calling / 工具调用 【有证据 · Day 1、Day 4】

**面试官**：工具调用你是怎么实现的？

> 核心是消息协议：模型返回 tool_calls，我执行工具，再把每条结果以 role=tool 加对应 tool_call_id 回填，然后让模型继续；顺序错了模型就读不懂。Schema 上我把名字和描述写成给模型看的使用说明——什么时候用、什么时候不用；参数尽量用枚举和格式约束，一个工具只干一件事。执行前先校验参数，写操作做幂等，避免重试产生重复副作用。错误统一转成可读结果回填，让模型自己收尾；多个不依赖的工具可以并行，但要限流、超时，并保证结果和 id 一一对应。

**追问“工具描述写不好会怎样？”**
“模型会选错工具或写错参数，比如语义重叠的工具容易被混用；我会做一套工具选择的小评测集来验证描述质量。”

### A5 RAG 检索增强 【有证据 · Day 3 最小实现；Day 9–10 升级】

**面试官**：检索不准你怎么排查？

> 我按链路拆成召回、排序、生成三段。第一步看答案所在的块有没有被检索到——没召回就是分块、查询或索引的问题；第二步看它有没有被排序挤出去——那是检索策略或 rerank 的问题；第三步资料在但模型没用或用了错的——那是 prompt 和上下文组装的问题。召回上做混合检索，关键词加向量、再融合；排序上先粗召回几十条，再 rerank 精排取 Top-k。上线前用召回率和 MRR 衡量检索，用引用正确率和忠实度衡量生成。

**追问“索引怎么更新？”**
“新增和修改走增量 upsert，删除同步，定期全量重建，保留版本和时间字段以便回滚。”

## B Agent 核心与编排

### B1 Agent 运行循环 【有证据 · Day 1–4】

**面试官**：你是怎么写 Agent 主循环的？为什么会失控？

> 主循环是“问模型 → 如果需要就调工具 → 把结果回填 → 再问”，直到模型不再请求工具。我用过两种表达：手写循环，和用 LangGraph 把它画成状态图——节点负责做什么，条件边负责下一步去哪。防失控靠三层：模型不再要工具是自然结束；max steps、时间、成本上限是硬兜底；检测到同一工具同一参数反复出现就打断。另外有一个不变量：只要 assistant 发了 tool_calls，就必须有一条对应的工具结果回填，否则状态不完整、循环也停不下来。

**追问“ReAct 和 Plan-and-Execute 怎么选？”**
“步骤不确定、需要边做边看用 ReAct；步骤可预判的长任务先规划再执行；生产里常用粗规划加每步 ReAct。”

### B2 工具调用循环与错误恢复 【有证据 · Day 2、Day 6】

**面试官**：工具连续失败两次，Agent 应该怎么办？

> 先把错误分类：超时、限流这类瞬时错误可以退避重试；参数错、权限错、404 这类永久错误不重试，要么改参数要么放弃；模型编造工具名这种协议错误，就把错误信息回填让它自纠。所有异常都转成 role=tool 的错误结果回填，而不是把进程打崩。同时按工具统计连续失败次数，满 2 次就不再真正执行，直接回填“放弃重试”，让模型向用户诚实收尾。写操作要带幂等键，避免重试造成重复副作用；多次失败后还可以降级到备用工具或转人工。

**追问“为什么错误要回填给模型而不是直接抛异常？”**
“因为模型需要知道发生了什么才能收尾；直接抛异常用户只会看到崩溃。”

### B3 主流 Agent 框架运用 【有证据 · Day 4，有脚手架辅助】

**面试官**：框架帮你做了什么、藏了什么坑？

> 我拿 LangGraph 做过对照：它把循环表达成状态图，节点加条件边，框架负责状态合并、边和循环的调度、条件分支、流式观测、检查点和递归上限；但节点里的模型调用、工具执行、错误处理和路由规则还是我自己写。坑主要有三个：抽象泄漏——出问题必须知道框架底层发的是什么请求；版本更新快；以及隐性成本，比如重试和状态重复传递。我的习惯是先手写一遍最小循环，再用框架提效，这样能说清哪部分是框架给的、哪部分是我做的。

**追问“LangChain / LlamaIndex 呢？”**
“LangChain 组件生态全、上手快；LlamaIndex 偏 RAG 和数据连接；选哪个看场景和团队熟悉度，但都要能下沉到原始请求排查。”

### B4 多 Agent 与工作流编排 【无证据 · 用设计思路答】

**面试官**：把一个复杂流程拆成多 Agent，你怎么设计？

> 我先问要不要拆：能用确定性工作流解决的就不上多 Agent，多 Agent 的价值主要在角色分工和上下文隔离。拆的时候按“可独立完成、结果可验证”划边界，常用模式有主管分派、流水线、层级团队和互审。通信我用共享 state 或消息传递，交接时明确传什么、丢什么。汇聚阶段要有冲突解决和去重。失败处理必须覆盖子任务超时、互相等待的死锁、循环交接和成本爆炸，所以每个子任务都要有步数、时间和预算上限，超时就降级或转人工。

**追问“多 Agent 一定更好吗？”**
“不一定，它的成本和调试复杂度都会上升；如果单 Agent 加清晰的工作流能解决，我更倾向单 Agent。”

### B5 状态、记忆与长任务 【无证据 · 用方法论答】

**面试官**：任务执行到一半进程挂了，怎么恢复？

> 我会把状态分层：会话状态、任务状态和长期记忆分开。每一步把任务状态写到检查点，任务用带 id 的队列驱动；重启后从最近的检查点恢复，已完成步骤靠幂等避免副作用重复。大的中间产物存对象存储，状态里只存引用。长期记忆只写稳定、可复用、有出处的事实，做去重和冲突处理；遗忘用 TTL 和重要性衰减，并且允许用户查看和删除，防止把一次错误结论写成长期事实。

**追问“怎么防止记错？”**
“区分用户说的和模型猜的，只写有出处的内容，冲突时保留历史并标记当前有效值。”

### B6 人机协同与执行监督 【无证据 · 用设计原则答】

**面试官**：哪些动作必须人工确认？怎么让用户信任 Agent？

> 不可逆或高影响的动作必须确认，比如付款、删除、对外发送、改生产配置，还有涉及权限隐私和模型置信度低的情况。确认时我会把“要做什么、影响范围、具体参数”展示清楚，确认绑定具体参数，防止确认后被改写，并支持超时撤销。信任来自三点：可解释——展示引用了什么、调了什么工具；可控——能打断、暂停、回滚，写操作先 dry-run 或最小权限；一致——不知道就说不确定，关键动作全程留痕可追溯。

## C 工具与生态

### C1 MCP 协议与 MCP Server 【无证据 · 阶段 2 才学，只答概念】

**面试官**：MCP 比普通 HTTP 工具多了什么？

> 我的理解是，MCP 是 LLM 应用和外部能力之间的标准协议，分 Host、Client、Server，统一暴露工具、资源、提示三类能力。相比自己写 HTTP 工具，它多了标准化的能力发现和 Schema 协商，写一次可以被多个客户端复用，调用和错误语义统一，传输层还能换——本地用 stdio，远端用 HTTP。安全上要做最小权限、工具白名单、参数校验和审计。我目前是在学习中，计划做一个最小 MCP Server 接入 Agent，所以细节还在补。

**追问“为什么不用普通函数调用？”**
“函数调用是我自己进程内的工具；MCP 解决的是跨进程、跨客户端复用和标准接入的问题。”

### C2 工具 / API 设计 【有证据 · Day 1–6 工具 schema】

**面试官**：给你一个工具 Schema，你能看出什么问题？

> 我先看给模型看的部分：名字语义是否单一、描述有没有写清“什么时候用、什么时候不用”、参数是不是用枚举和格式约束、必填项是否明确。典型问题有三个：描述含糊，比如“处理数据”；参数太自由，比如一个 options 字符串塞所有东西；多个工具语义重叠，模型会混用。然后看安全：有没有资源范围限定和最小权限，能不能删任意 id。返回值我会尽量小、错误要可操作，大结果分页或给句柄。

**追问“写操作怎么设计？”**
“幂等键、参数校验、必要时人工确认或 dry-run，并记录审计日志。”

### C3 记忆系统设计 【无证据 · 用设计思路答】

**面试官**：用户画像和项目历史该存哪、怎么更新？

> 我只存稳定事实和可复用结论，不存一次性噪声。结构化字段放关系库或 KV，语义检索类的放向量库，关系复杂用图，原始对话归档做证据链。写入流程是先抽取候选，再去重和冲突判定，必要时人工确认后落库，每条都带来源和时间。更新时新证据覆盖旧值，冲突就保留历史并标记当前有效值。防污染的关键是只写有出处的内容，区分用户说的和模型猜的，并允许用户查看和删除。

**追问“怎么评估记忆有没有用？”**
“看写入准确率、检索命中率，以及对任务成功率有没有实际提升。”

### C4 外部系统集成 【部分证据 · 后端集成经验可迁移】

**面试官**：把“自动建单 + 通知”串成工具链，你会注意什么？

> 我会按四块设计。鉴权用 OAuth 或服务账号，密钥不落进模型上下文，权限按最小范围申请，测试和生产分开。可靠性上做超时、退避重试、限流、幂等键和失败补偿，写操作要能查“是否已经生效”。数据上处理字段映射、时区和编码，分页用 cursor 做增量拉取，错误码统一归一化。可观测上每次外部调用都留 trace：耗时、响应码和请求 id，方便跨系统对账。对外或不可逆动作加人工确认。

**追问“重试会不会重复建单？”**
“所以写接口必须幂等，用业务幂等键；重试前先查状态，而不是盲目重发。”

### C5 代码执行与沙箱安全 【无证据 · 用设计原则答】

**面试官**：让 Agent 执行生成的代码，怎么保证安全？

> 我会用容器或微虚拟机隔离，默认无网络、根文件系统只读，只给一个临时可写目录；限制 CPU、内存、磁盘和执行时间，超时直接杀。权限上跑非 root 用户，限制系统调用，禁止访问宿主敏感路径和凭证。动作上做命令白名单和危险操作扫描，需要联网或写外部系统时必须审批。所有执行的代码、输入输出和资源使用都记录，方便重放和回滚，产物导出单独管控，防止数据外泄。

## D 评测与质量

### D1 Eval 数据集与场景设计 【无证据 · 用方法论答】

**面试官**：给一个 Agent 场景设计 10 条 Eval 用例，你怎么设计？

> 我从真实日志和用户问题里取样，不自造。覆盖三类：高频正常路径、已知失败模式、边界情况，比如空输入、超长输入、缺参数和恶意输入。用例分层：单工具正确性、单轮工具选择、多轮任务完成、端到端。每条写清输入、前置状态、期望行为和必须拒绝的行为。能确定性校验的就写断言，比如工具有没有被调、参数对不对；开放生成才用评分规则或裁判。最后画一张能力乘场景的矩阵，确认每个关键能力都有用例，失败样例回归进套件。

**追问“为什么不自造用例？”**
“自造容易只覆盖自己想到的路径；真实数据里的长尾才是失败集中区。”

### D2 LLM-as-Judge 【无证据 · 用方法论答】

**面试官**：LLM 当裁判会自嗨吗？怎么发现它不可靠？

> 会有偏差：位置偏差、长度偏差，还有偏爱自己家模型的输出。所以我会用成对比较并交换位置取平均，给明确的评分量表和反例做参照，必要时用多个裁判投票。校准上拿人工标注的样本对裁判做一致性检验，不达标就改量表或换模型。还有一个原则：能用规则或断言判的绝不交给裁判，裁判只做需要语义判断的部分。裁判版本和温度固定，结果缓存，升级后必须重跑回归。

**追问“怎么防位置偏差？”**
“同一对答案换顺序各评一次，两次结果平均或取一致结论。”

### D3 可观测性与调试 【有证据 · Day 4 流式观察】

**面试官**：Agent 成功率下降，你第一步看什么？

> 我先按时间线定位“从哪一步开始变差”，找到变更点——是模型版本、prompt、检索还是某个工具，而不是直接改 prompt。然后看每次模型调用的输入输出和 token、工具调用的参数和结果、检索命中的文档和分数、耗时和错误码、重试次数。Trace 要能重放：带请求 id、模型版本、prompt 版本和配置快照，同一输入能不能复现。归因就分检索、工具、模型或 prompt、数据权限、环境几类。我在 LangGraph 项目里用 stream 的 updates 模式观察每个节点的状态更新，就是最小可观测性实践。

**追问“报警看什么指标？”**
“成功率、p95 延迟、单位任务成本、工具错误率、检索命中率。”

### D4 Guardrail、安全与合规 【无证据 · 用原则答】

**面试官**：用户让 Agent“忘掉安全规则”，怎么防？

> 我的原则是不靠模型自觉，把安全放在模型之外：工具权限、参数校验、审批流和沙箱。Prompt 注入的防护是把外部内容当数据、和指令分区，关键动作二次校验。权限上工具只暴露必要能力和资源范围，写操作显式授权，敏感数据脱敏后再进上下文。输出侧做敏感信息过滤和内容合规检查。所有高风险动作留审计日志，支持追溯和回滚，并用红队用例做回归测试。

**追问“为什么不直接在 system prompt 里写不许？”**
“因为提示可以被绕过，真正的边界要在权限和工具层强制执行。”

### D5 效果 / 成本 / 延迟优化 【有证据 · Day 2/6 限流意识】

**面试官**：一个高频 Agent 任务太贵太慢，怎么优化？

> 先度量：单位任务成本，也就是 token 用量乘单价，和 p50、p95 延迟，找出最大头——是输入上下文、重试还是检索。然后分几层优化：模型上按任务分层路由，简单任务用小模型，系统提示用缓存；上下文上裁剪历史、做摘要、检索前置过滤，把长工具结果压成要点加引用；架构上并行调用互不依赖的工具、流式输出改善首字延迟、加超时和降级、做结果缓存。每次优化后用同一套 eval 对比，防止低成本换来低质量。

**追问“成本降到一半但质量掉了怎么办？”**
“用同一套评测回归，设质量红线；不达标就只在低风险子任务上使用降本方案。”

## E Python 工程能力

### E1 Python 语言惯用法与类型标注 【有证据 · Day 5；独立验证待 Day 8】

**面试官**：你怎么判断一份 Python 代码写得“像 Python”？

> 我先看类型和结构：公共函数有没有类型标注，数据模型用 dataclass 或 Pydantic，固定取值用 Enum，固定形状的字典用 TypedDict。再看控制流：会不会用字典分发或注册表代替长串 if/elif，遍历用 enumerate 和 zip，而不是手写下标。异常上捕获具体类型、保留 raise from 的因果，不用裸 except 吞掉错误。函数设计上优先小函数和纯函数，外部依赖用注入而不是硬编码，方便测试。最后用 ruff 和 mypy 把格式、lint 和类型检查跑通。我在 Day 5 的项目里把工具分发改成注册表、给 run_agent 加了依赖注入，就是为了这些。

**追问“依赖注入好在哪？”**
“把外部边界变成参数，测试可以注入假模型，离线、确定、不需要密钥。”

### E2 async 与并发 【无证据 · 有接触，按计划答】

**面试官**：怎么并发调用多个工具，并做限流和超时？

> 用 asyncio，多个互不依赖的工具用 gather 并发，或者用 TaskGroup 做结构化并发，一处失败统一取消。限流用 Semaphore 控制并发数，超时用 timeout 包住每次调用，超时要能取消底层请求。注意不能在协程里做阻塞 IO，同步 SDK 要放 to_thread；HTTP 用异步客户端加连接池。并发安全上避免共享可变状态，注意取消时的清理和幂等。错误策略可以收集部分失败，也可以要求全成功，看业务。我目前这块主要是学习和准备实践，还没在生产项目里用过。

**追问“并发一定更快吗？”**
“不一定，受配额和下游限流影响；要测 p95 延迟和整体吞吐，必要时串行或分批。”

### E3 FastAPI / Web 服务与流式输出 【接触过 rag-demo 的 SSE】

**面试官**：你怎么实现带 SSE 的 Agent 对话接口？

> 我会分成普通接口和流式接口：普通接口直接返回结果，流式用 StreamingResponse 输出 text/event-stream，事件按 data 加换行的格式发，并加定时心跳防止代理超时，客户端断开时要停止生成并释放资源。请求和响应用 Pydantic 建模，错误返回统一结构，带 code 和 request id。链路全异步，避免阻塞事件循环；连接池和客户端用 lifespan 管理，保证优雅退出。中间件上加请求 id、日志和 CORS，反代下要关闭缓冲，否则流会被攒住。测试用 TestClient 或 httpx 校验事件序列。

**追问“为什么用 SSE 不用 WebSocket？”**
“单向流式输出 SSE 更简单、对代理友好；需要双向交互或二进制再考虑 WebSocket。”

### E4 测试与代码质量 【有证据 · Day 5/6，其中部分为教练代写】

**面试官**：给这个任务补测试，你会怎么做？

> 先做可测性设计：把外部边界——LLM、HTTP、时钟、随机数——变成可注入参数，这是能不能写单测的前提。测试替身我用手写假函数或 mock 替换外部调用，断言行为契约，比如消息序列、role、tool_call_id、调用次数，而不是实现细节。用例分层：纯函数单测、循环和路由单测、工具 schema 与注册表的一致性测试，再配少量端到端。失败路径必须覆盖：错误回填、重试上限、超时、空结果、非法参数。测试要离线、确定、不依赖网络和密钥，最后用 ruff、mypy 和 CI 保证质量。

**追问“怎么避免测试过拟合实现？”**
“断言行为而不是内部结构：改动实现但行为不变时，测试应该照样通过。”

### E5 Python 工程化 【无证据 · 按最佳实践答】

**面试官**：一个 Python 项目，你会怎么做工程化？

> 依赖和打包用 uv 加 pyproject，提交 lockfile，src 布局，保证可复现。配置从环境变量读并用 Pydantic 校验，.env 和密钥不入库，也不写进日志或模型上下文。日志用结构化 JSON，带 request id 或任务 id，贯穿工具和模型调用，敏感字段脱敏。边界数据用 Pydantic 校验，内部用 dataclass 或 TypedDict。CI 跑 lint、类型检查、单测和构建，pre-commit 挡住低级错误。我现在这块主要是照最佳实践在做，还没有完整的 CI 流水线经验。

**追问“密钥怎么管理？”**
“环境变量或密钥管理服务，最小权限、可轮换；绝不入库、不进日志、不进 prompt。”

### E6 独立排查与调试 【有证据 · Day 4；独立验证在 Day 8】

**面试官**：给你一个报错，你怎么定位？

> 我先读 traceback，从最底部的真正异常往上看调用栈，确认异常类型和位置，再判断业务含义。然后固定输入复现，逐步删减到最小可复现片段，写清预期和实际的差异。定位时在边界打日志或断言状态——类型、长度、关键字段，必要时二分注释或用调试器。一次只改一个变量，先证伪最可能的原因，对比正常和异常路径的差异。修复时先写一个能复现失败的测试，再改到绿，最后跑全量回归。像我在 LangGraph 项目里遇到的那个问题，就是先用 stream 的 updates 看到节点提交是空，才定位到状态键名不匹配。

**追问“改完之后怎么确认没有引入新问题？”**
“跑全量测试和回归用例，必要时加一条针对根因的回归测试。”

## F 求职交付

### F1 项目叙事与贡献边界 【无证据 · 有素材，需先演练】

**面试官**：挑一个项目，讲讲你的贡献。

> 我会用 STAR 结构：先说背景和目标，再说我的任务、我做的关键动作和取舍，最后给可量化的结果——比如成功率、成本、时延或迭代次数。贡献边界我会讲清楚哪些是我设计实现、哪些是团队协作，AI 参与度高的话我也如实说明哪些是 AI 产出、我做了什么验证和改造。重点讲两三个权衡，比如为什么这样分块、为什么这样限流，以及被否掉的方案。这样追问细节时都能落到依据上。

**追问“AI 生成的部分怎么算你的贡献？”**
“我不会把 AI 生成当成自己的能力证明；我会讲清验收标准、我改了什么、为什么这么改。”

### F2 Agent 系统设计表达 【无证据 · 用设计框架答】

**面试官**：现场设计一个多 Agent 系统。

> 我先澄清需求：用户是谁、规模和并发、延迟和成本预算、失败容忍度、数据和合规约束。然后画分层：客户端到 API 网关，到编排层——单 Agent 或 LangGraph，再到工具和检索，最后是模型、存储和可观测。接着讲关键设计：状态和记忆放哪、工具怎么注册鉴权和限流、失败怎么重试降级、哪些动作要人工确认、怎么灰度和评测。我会主动讲失败路径，比如模型超时、工具挂了、检索为空、上下文超限和成本失控分别怎么兜，并说明为什么不选更简单的方案。

**追问“为什么不用多 Agent？”**
“多 Agent 的收益是角色分工和上下文隔离，代价是成本和调试复杂度；如果单 Agent 加确定性工作流能解决，我先用单 Agent。”

### F3 JD 对齐与简历表达 【部分证据 · jd_library 已建】

**面试官**：这段 JD 要求，对应你哪个证据？

> 我先把 JD 拆成必须项、加分项和加分点，标注每条对应哪个能力项。然后建一张证据表，每个必须项至少对应一条证据——项目、代码、指标或复盘；证据不足的我列入学习计划，而不是硬写。写简历时用动作加技术加结果，结果尽量量化，用 JD 的关键词对齐但不虚构。每个核心要求准备两三个能深挖的故事，并提前想好“这个缺口我准备怎么补”。投递前我会先做能力达标判断，不达标的岗位不投，避免浪费双方时间。

**追问“没有相关经验怎么办？”**
“如实说明没有实战，同时给出相邻经验、我准备怎么补、以及已经做过的练习证据。”

### F4 面试应对与追问 【无证据 · 有原则，需演练】

**面试官**：（连续追问到你不熟的领域）
