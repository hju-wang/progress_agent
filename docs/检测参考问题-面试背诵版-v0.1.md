## A 大模型基础与应用

### A1 模型选型（别硬吹）

**面试官**：这个场景你怎么选模型？

> 这块我没什么生产选型经验，只能说思路。我先看任务本身，是要它做分类抽取这种有标准答案的活，还是要它多步推理、写长文。前者小模型就够了，便宜也快；后者才上大模型或者推理模型。然后看成本、延迟这些限制，还有上下文多长、支不支持工具调用、数据能不能出内网。选完我会拿自己场景的一小套题去跑，看通过率、单次成本和响应时间，不太敢只看榜单。上线前会留个备选模型，主模型限流或者超时的时候能切过去。

### A2 提示词和结构化输出（能举例，Day 1–3）

**面试官**：怎么保证模型输出能直接被程序用？

> 这个我实际做过。我的做法是不指望模型“听话”，直接上 function calling 或者 JSON Schema，把字段、类型、枚举、必填项都卡死，而不是在 prompt 里写一句“请输出 JSON”。prompt 那边我会写清楚角色和约束，信息不够的时候允许它说不知道。拿到输出之后还有一层：解析失败就把错误信息带上重试一次，或者降级解析；解析成功也要做业务校验，比如枚举值合不合法、数字有没有超范围。我在 Day 1 写工具 schema 的时候就是这么干的。

### A3 上下文管理（别硬吹）

**面试官**：多轮对话历史一直涨怎么办？

> 我会先算一笔账：system、工具描述、检索资料、历史、输出各留多少 token，超了从哪儿砍得提前定。然后分层处理，最近几轮留原文，更早的滚成摘要，长期有用的事实丢到外部存储，用到再捞回来。工具返回的大段内容用完就丢，检索到的原文压成要点加引用。任务进行到哪一步这种信息，我会放在结构化的 state 里，不塞在聊天记录里，这样断了还能续。顺序上我先做结构化状态，再做摘要，最后才考虑扩大上下文窗口，窗口大不代表该往里塞。

### A4 工具调用（能举例，Day 1、Day 4）

**面试官**：工具调用你是怎么实现的？

> 关键是消息要接得上。模型返回 tool_calls，我执行工具，然后每条结果用 role=tool、带上对应的 tool_call_id 再喂回去，模型才知道这条结果是它要的那次调用，顺序错了它就懵。工具的描述我会当文档写，讲清楚什么时候用、什么时候别用，参数尽量用枚举，一个工具只干一件事。执行前先校验参数，写操作得幂等，不然重试一次就重复下单了。出错的时候我不抛异常，转成一条错误结果喂回去，让模型自己收尾。Day 1 和 Day 4 我都写过这套循环。

### A5 RAG（Day 3 做过玩具版，Day 9–10 要升级）

**面试官**：检索不准你怎么查？

> 我在 Day 3 做过一个很小的 RAG：自己分块、用共同词打分、把命中的资料回填给模型，让它带着来源回答。但那是玩具，没有 embedding 和向量库，所以往大里说我不敢讲。排查思路我是按三段走的：先看答案所在的那块有没有被召回，没有就是分块、查询词或者索引的问题；召回了但排在后面没进上下文，那是排序的问题，得加重排；资料明明在上下文里模型还是答错，那是提示词和拼装的问题。真上规模我会做关键词加向量的混合检索，再拿召回率和 MRR 去看效果。

## B Agent 核心与编排

### B1 Agent 运行循环（能举例，Day 1–4）

**面试官**：主循环怎么写的？为什么会转不停？

> 我写过两种。一种是手写的：问模型，要工具就执行，结果喂回去，再问，直到模型不再要工具。后来 Day 4 用 LangGraph 又把同一个循环画成了图，节点负责干活，条件边负责下一步往哪走。防转不停我有三层：模型自己不要工具是最正常的结束；步数、时间、成本是硬上限；再就是发现同一个工具配同一组参数反复出现，直接打断。另外有个不变量我一直守着：只要模型发了 tool_calls，就必须回一条对应的工具结果，少一条状态就不完整，循环也停不下来。

### B2 工具调用错误恢复（能举例，Day 2、Day 6）

**面试官**：工具连着失败两次，怎么办？

> 先分是什么错。超时、限流这种过一会儿就好，退避重试；参数写错、没权限、404 这种重试也没用，要么改参数要么放弃；模型自己编了个不存在的工具名，那就把错误信息喂回去让它自己改。不管哪种，异常我都转成一条 role=tool 的结果喂回去，不会让进程崩掉。然后我会按工具记连续失败次数，满两次就不再真调了，直接回一条“放弃重试”，让它老实告诉用户。写操作带幂等键，避免重试把订单建两遍。Day 2 做的是错误回填，Day 6 补的是这个熔断。

### B3 框架（能举例，Day 4；当时有脚手架辅助）

**面试官**：用框架省了你什么？有什么坑？

> Day 4 我用 LangGraph 对照做过一遍。它替我管状态怎么合并、节点和条件边怎么调度、流式怎么看每一步，还有检查点和递归上限；但节点里面的模型调用、工具执行、错误处理、路由判断，都还是我写。坑我觉得有三个：一是抽象泄漏，真出问题你得知道它底层发了什么请求；二是版本变得快；三是隐形成本，重试和状态重复传递会让 token 涨。我的习惯是先手写一遍最小循环再用框架，这样能说清哪部分是框架的、哪部分是我的。

### B4 多 Agent（别硬吹）

**面试官**：复杂流程怎么拆成多个 Agent？

> 这块我没做过，只能讲设计思路。我会先问要不要拆——能用确定性流程解决的，我不太想上多 Agent，因为成本和调试难度都上去了。真拆的话，按“这件事能不能独立做完、结果能不能验证”来划边界，常见的是主管分派、流水线、互相评审这几种。Agent 之间要么共享状态，要么传消息，交接的时候得说清楚传什么、丢什么。最后要有人负责汇总和冲突处理。失败情况我会提前想：子任务超时、两个 Agent 互相等、来回踢皮球、成本失控，这些都得有步数和时间上限。

### B5 状态、记忆、长任务（别硬吹）

**面试官**：任务跑到一半进程挂了，怎么恢复？

> 我会把状态分开看：会话状态、任务进度、长期记忆。任务每走一步就把进度写到一个检查点，任务本身用带 id 的队列驱动，重启以后从最近一次检查点接着跑，已经做完的步骤靠幂等避免副作用重复。大的中间产物丢对象存储，状态里只留个引用。长期记忆我只写稳定、以后用得上、有出处的东西，写之前去重，有冲突就留最新并记下来源。遗忘用 TTL 和重要性衰减，用户也得能看和能删，不然记错了很麻烦。

### B6 人机协同（别硬吹）

**面试官**：哪些动作要人确认？怎么让人信任 Agent？

> 不可逆的、影响大的都要确认，比如付款、删除、对外发消息、改生产配置；涉及权限和隐私的也要。确认的时候不能只弹个“是否继续”，得把要做什么、影响范围、具体参数摆出来，确认要绑在这次具体的参数上，不然确认完参数被改了就白确认。信任我觉得来自三件事：能解释，告诉你它引用了什么、调了什么；能控制，能打断、能暂停、能回滚，写操作先干跑一遍；还有一致，不知道就说不知道。关键动作全程留痕，出问题能查。

## C 工具与生态

### C1 MCP（别硬吹，还没学）

**面试官**：MCP 比普通 HTTP 工具多了什么？

> 老实说这块我还在学，没做过。我的理解是，MCP 是给 LLM 应用和外部能力之间的一个标准协议，分 Host、Client、Server，统一暴露工具、资源、提示这几类东西。跟自己写 HTTP 工具比，它多了标准的能力发现和参数描述，写一次能被多个客户端复用，传输方式也能换，本地走 stdio，远端走 HTTP。安全上还是老一套：最小权限、工具白名单、参数校验、审计。我计划下一步写一个最小的 MCP Server 接进 Agent，现在细节还不敢说太满。

### C2 工具和 API 设计（能举例，Day 1–6 的工具 schema）

**面试官**：给你一个工具定义，你能看出什么问题？

> 我先看给模型看的那部分：名字是不是只干一件事，描述有没有说清楚什么时候用、什么时候别用，参数是不是能枚举就枚举。常见毛病是描述含糊，比如“处理数据”；或者参数太自由，一个 options 字符串什么都往里塞；还有就是几个工具意思重叠，模型肯定混着用。然后看安全，比如这个工具能不能删任意 id，权限是不是太大了。返回结果我尽量给小的、有用的字段，错了要告诉模型怎么改，大结果就分页或者给个句柄。我在 Day 1 到 Day 6 写工具 schema 的时候就是按这个标准来的。

### C3 记忆系统（别硬吹）

**面试官**：用户画像和项目历史存哪儿、怎么更新？

> 这块我没系统做过。我的想法是只存稳定的东西，一次性的聊天内容别往里塞。结构化的字段放关系库或者 KV，要做语义检索的放向量库，关系复杂的用图，原始对话存档留着当证据。写进去之前先抽候选，去重、看有没有冲突，有必要就让人确认一下，每条都记来源和时间。更新就是新的覆盖旧的，冲突的时候两个都留着，标一下哪个是当前有效的。最容易出问题的是把模型猜的东西当成事实写进去，所以一定要分清楚哪句是用户说的、哪句是模型推的。

### C4 外部系统集成（有后端经验，但 Agent 工具链没做过）

**面试官**：自动建单加通知这种链路，你会注意什么？

> 我之前做后端的时候对接过不少系统，思路是通的，但用 Agent 串起来还没做过。鉴权用 OAuth 或者服务账号，密钥不能进模型上下文，权限按最小来，测试和生产要分开。可靠性上就是超时、退避重试、限流、幂等这几件，写操作得能查“是不是已经生效了”，不能瞎重发。数据上处理字段对应、时区、编码，分页用游标做增量。每次外部调用都留痕，耗时、返回码、请求 id，对不上账的时候能查。对外的动作加人工确认。

### C5 代码执行沙箱（别硬吹）

**面试官**：让 Agent 跑生成的代码，怎么保证安全？

> 我没在生产做过，讲下思路。执行环境要用容器或者微虚拟机隔开，默认不通网，根目录只读，只给一个临时目录能写。资源上限制 CPU、内存、磁盘和时间，超时就杀。权限上跑非 root，限制系统调用，别让它碰到宿主机上的敏感路径和密钥。动作上做命令白名单，扫一遍危险操作，要联网或者要写外部系统的必须走审批。执行过的代码、输入输出、资源占用都记下来，方便回放，产物导出另外管。

## D 评测与质量

### D1 Eval 数据集（别硬吹）

**面试官**：给一个 Agent 场景设计 10 条评测用例，你怎么下手？

> 我会从真实日志和用户问题里挑，不太敢自己编，自己编只能覆盖自己想到的路径。挑的时候覆盖三类：正常高频的、已知会翻车的、边界的，比如空输入、超长输入、少参数、恶意输入。用例也分层，单工具对不对、单轮工具选得对不对、多轮任务做完没有、再到端到端。每条写清楚输入、前置状态、期望行为，还有绝对不能做的事。能写断言的就不上裁判，比如工具有没有调、参数对不对。最后画一张能力和场景的矩阵，看看哪个能力还没覆盖到。

### D2 LLM 当裁判（别硬吹）

**面试官**：LLM 裁判会不会自嗨？怎么发现它不靠谱？

> 会，位置偏差、长度偏差都有，还容易偏爱自己家的模型。我会用成对比较，然后把两个答案换个位置再评一次，取平均；评分标准写细一点，配几个反例；必要时多找几个模型投票。更关键的是拿人工标过的样本去对，一致率不行就改标准或者换模型。还有一条，能用规则和断言判的绝不交给裁判，裁判只用来判那些真需要语义理解的部分。裁判的版本和温度固定住，升级了必须把回归重跑一遍。

### D3 可观测性（能举例，Day 4）

**面试官**：Agent 成功率掉了，你第一步看什么？

> 我会先看时间线，找到是从哪一步开始掉下来的，对应最近改了什么——换模型了、改 prompt 了、检索变了还是某个工具挂了，而不是上来就改 prompt。然后看每次调用的输入输出和 token、工具的参数和结果、检索命中了哪些文档、耗时和错误码。trace 要能重放，带请求 id、模型版本、prompt 版本，这样同一输入能不能复现就清楚了。Day 4 排查那个状态不更新的问题时，我就是用 stream 的 updates 模式看每个节点到底提交了什么，一看是空的，就知道问题在状态那层。

### D4 安全护栏（别硬吹）

**面试官**：用户让 Agent“忘掉安全规则”，怎么防？

> 我的思路是别指望模型自觉，安全得放在模型外面：工具权限、参数校验、审批、沙箱。注入这块，把用户输入和检索到的内容都当数据，不当指令，关键动作再做一次校验。工具只给必要的能力和资源范围，写操作要显式授权，敏感信息脱敏之后再进上下文。输出那边做敏感信息过滤。高风险的动作全部留审计日志，能追能回滚，平时准备一些红队用例当回归。

### D5 成本和延迟（有点意识，Day 2、Day 6）

**面试官**：一个高频任务又贵又慢，怎么优化？

> 先量，别拍脑袋。算单位任务成本，也就是 token 乘单价，再看 p50 和 p95 延迟，找到大头是输入太长、重试太多还是检索太慢。然后分几层动：简单任务换小模型，固定的系统提示用缓存；上下文该裁的裁、该摘要的摘要，检索先过滤再把长结果压成要点；架构上把互不依赖的工具并行，流式输出让首字快一点，加超时和降级，结果能缓存就缓存。我自己在 Day 2 和 Day 6 做限流，就是因为看到坏工具被反复调用会一直烧 token。每次优化完都得用同一套评测跑一遍，别把质量换没了。

## E Python 工程能力

### E1 Python 惯用法（能举例，Day 5；独立性后面还要验）

**面试官**：你怎么看一段 Python 写得地不地道？

> 我先看类型和结构：公共函数有没有类型标注，数据模型用 dataclass 还是 Pydantic，固定取值用 Enum，固定形状的字典用 TypedDict。再看控制流，长串的 if/elif 我会换成字典分发，遍历用 enumerate 和 zip，不手写下标。异常这块，捕具体的类型，保留 raise from 的因果，不用裸 except 把错误吞掉。函数尽量小，外部依赖用参数传进来而不是写死，这样好测。最后用 ruff 和 mypy 过一遍。Day 5 我把工具分发改成注册表、把 run_agent 的 llm 改成可以注入的参数，就是这两个点。

### E2 async 并发（没写过，别吹）

**面试官**：怎么并发调多个工具，还做限流和超时？

> 我了解做法，但没在生产写过。用 asyncio，几个互不依赖的调用用 gather 并发，或者 TaskGroup 做结构化并发，一处失败统一取消。并发数用 Semaphore 卡住，超时用 timeout 包住，超时得能真的取消底层请求。有个坑是不能在协程里做阻塞 IO，同步的 SDK 要丢到线程里；HTTP 用异步客户端加连接池。共享可变状态尽量别碰，注意取消时的清理。这块我是准备在 W41 里补一个真练习，现在只能讲到这个程度。

### E3 FastAPI 和 SSE（只在 rag-demo 接触过）

**面试官**：带 SSE 的 Agent 接口你怎么做？

> 我在之前的 rag-demo 里接触过 SSE，但没独立交付过。做法大概是普通接口直接返回，流式用 StreamingResponse 发 text/event-stream，事件按 data 加换行的格式发，中间加心跳，免得被代理掐了；客户端断开要停掉生成、释放资源。请求和响应用 Pydantic 建模，错误统一结构，带上请求 id。整条链路要异步，别阻塞事件循环；连接池这些东西用 lifespan 管，退出的时候要优雅。反代下面记得关 buffering，不然流会被攒着一起发。测试用 TestClient 或者 httpx 校验事件序列。

### E4 测试（能举例，Day 5/6；但 Day 6 的测试是教练代写的）

**面试官**：这个任务你怎么补测试？

> 先把外部的东西变成能替换的：LLM、HTTP、时钟这些做成参数，这是能不能写单测的前提。测试里用假函数或者 mock 顶掉外部调用，断言的是行为，比如消息序列长什么样、role 对不对、tool_call_id 有没有丢、调了几次，而不是去看内部怎么实现。用例分几层：纯函数、循环和路由、工具 schema 和注册表的一致性，再加少量端到端。失败路径必须覆盖，错误回填、重试上限、超时、空结果这些。测试要离线、确定，不依赖网络和密钥。Day 5 我写了五个用例；Day 6 那两个限流的用例是教练代写的，所以这部分我得再独立做一次才算数。

### E5 工程化（没做过完整的，不吹）

**面试官**：一个 Python 项目你会怎么做工程化？

> 我还没做过完整的 CI 流水线，按我了解的说。依赖用 uv 加 pyproject 管，锁文件提交，src 布局，保证换台机器能装出一样的环境。配置从环境变量读，用 Pydantic 校验一下，.env 和密钥别进库，也别进日志和 prompt。日志用结构化的，带 request id，敏感字段脱敏。边界数据用 Pydantic 验，内部用 dataclass 或者 TypedDict。CI 里跑 lint、类型检查、单测、构建，pre-commit 挡一些低级错误。这些我是在逐步补，还没有一整套跑起来。

### E6 排查和调试（能举例，Day 4；独立验证在 Day 8）

**面试官**：给你一个报错，你怎么定位？

> 先看 traceback，从最底下真正的那个异常往上看调用栈，弄清错在哪、什么类型，再看业务上意味着什么。然后固定输入把它复现，一点点删到最小片段，写清楚预期的和实际的差在哪。定位的时候我在关键边界打日志或者断言状态，类型、长度、关键字段对不对，实在不行就二分注释。一次只动一个地方，先把自己觉得最可能的原因证伪。改之前先写个能复现失败的测试，改到绿，再跑全量回归。Day 4 那个状态不更新的问题，就是我先用 stream 的 updates 看到节点提交是空的，才把范围缩到状态键名上的。

## F 求职交付

### F1 项目叙事（还没演练过）

**面试官**：挑一个项目，讲讲你的贡献。

> 我还没做过正式的 mock，先讲我的准备方式。我会按背景、任务、动作、结果来讲，结果尽量带数字。个人贡献会分开说：哪些是我设计的、哪些是我写的、哪些是团队一起的。AI 帮了多少我也会如实讲，会说明我拿什么标准验收、改了什么、为什么改，不会把 AI 生成的东西算成自己的本事。重点准备两三个取舍，比如为什么这么分块、为什么加熔断，还有当时放弃的方案是什么。

### F2 系统设计表达（还没练，先给框架）

**面试官**：现场设计一个多 Agent 系统。

> 我会先把需求问清楚：谁用、多少并发、延迟和成本能接受多少、失败了能不能忍、数据有没有合规要求。然后分层画：客户端到网关，到编排层，单 Agent 或者 LangGraph，再到工具和检索，最后是模型、存储和监控。接着讲几个关键点：状态和记忆放哪、工具怎么注册和鉴权、失败怎么重试和降级、哪些动作要人工确认、怎么评测和灰度。失败路径我会主动说：模型超时、工具挂了、检索为空、上下文爆了、成本失控分别怎么兜。最后说明为什么没选更简单的方案。

### F3 JD 对齐（做过一半，jd 库建了）

**面试官**：这条 JD 要求，对应你哪个证据？

> 我先把 JD 拆成必须项、加分项，标出每条对应哪个能力。然后做一张证据表，每个必须项至少配一条证据，项目、代码、指标或者复盘；凑不出证据的就列进学习计划，不硬写。写简历就是动作加技术加结果，结果尽量量化，关键词跟着 JD 走但事实不能改。每个核心要求我会准备两三个能深挖的故事，另外把“这块我缺，打算怎么补”也想好。投之前先判断自己够不够，不够就不投，省得两边浪费时间。目前 jd 库我建好了，简历对齐还没正式做过一轮。

### F4 面试应对（还没演练）

**面试官**：（一直追问到你不熟的领域）

> 这块我没实战过，就不编了。我知道的相邻部分是——（说已知的），如果让我做，我会先这么试——（给思路），也想听听你们实际是怎么处理的。设计题我会先问清楚约束再动笔，不会的时候把大问题拆成能回答的小问题，边想边说。失败的经历我会讲清楚根因、怎么修的、后来怎么防的，不装成一路顺利。最后我也会准备几个反问，比如你们怎么评估效果、线上出问题怎么处理、上线节奏大概什么样。
